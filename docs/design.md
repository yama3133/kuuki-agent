# Kuuki: 空気を読んで口を挟む会議エージェント 設計書

応募先: Agent Experience Hackathon: Strands Decider(締切 2026-10-23 23:59 GMT-7 = 2026-10-24 15:59 JST)
宣言する決定パターン: #policy(募集ページの定義「Classify an incoming request into a category before the agent acts on it」に対し、発言1つ1つを「黙る/事実確認/質問に答える/まとめる/脱線を戻す」に分類してから動く、という形で合わせる)

## 1. ひとことで

会議の発言が1つ入るたびに、Strands Decider 2B が手元の Mac で「いま口を挟むべきか」「挟むなら何をするか」を判定する。挟むと決めたときだけ Amazon Bedrock の LLM が発言を作り、読み上げる。

売り文句(英語の記事・動画用): "An AI meeting agent that knows when to stay quiet."
日本語の「空気を読む」を名前と体験の軸にする。ほとんどの時間は黙っていて、必要な瞬間だけ口を開く様子をデモで見せる。

## 2. 公式資料で確認した前提

- API: `POST /v1/systemone` に `state`(文字列)と `questions`(名前付きの質問)を送る。質問の型は `noul`(yes/no、P(yes) を返す)・`choice`(N択、選択肢ごとの確率と confidence)・`score`(順序付き尺度)
- 1回の呼び出しで複数の質問をまとめて送れる。state のエンコードは1回で済むので、質問を分けて送るより安い
- Strands 連携の公式例: `strands.interventions` の `InterventionHandler.before_tool_call` で判定し、`Proceed`(実行)か `Guide`(差し戻して考え直させる)を返す
- 参照モデル: `StrandsAgents/strands-decider-2B-qwen3.5-v1-2610`。README の遅延値は v19 の M3 Pro での計測で、温まった状態・300トークン未満で1問あたり中央値 153ms、全タスクでは 234ms。本設計の state は300トークンを超える見込みで、手元の M1 での値は未計測
- Apple silicon では、ある入力長で最初に来たリクエストだけ数秒遅れる(MPS の形状コンパイル。公式の `_client.py` のコメントより)。MLX で同じことが起きるかは未確認

README には「confidence 0.9 以上の回答は未知の短い分類タスクで約95%正解、それ未満は確認するか人に聞くこと」とある。本設計では、この確信度を「迷ったら黙る」という方針に使う。ただしこれは短い分類タスクでの値で、会議の文脈でも確信度と実際の正解率が合うかは、評価用台本で確かめる。

## 3. 全体の流れ

```
会議の発言(台本JSONLを実時間で再生 / 余力があればマイク入力)
  │ 1発言ごと
  ▼
InterjectionGate(Decider 2B、ローカル)
  │ 質問3つを1回で送る → 確率
  ▼
方針(ふつうのPython: しきい値・クールダウン・迷ったら黙る)
  ├─ 黙る ──────────→ 画面に確率だけ表示
  └─ 挟む(意図つき)→ Strands Agent(Bedrock)が発言を生成 → 読み上げ・画面表示
```

LLM を呼ぶのは「挟む」と判定した発言だけにする。毎発言で LLM に判定させる構成と比べて、遅延とコストの差を実測する(7章)。

## 4. Decider に渡す判定

### state の組み立て

- 会議の議題と参考資料の要約(数行)
- 直近の発言8件ほど(話者名つき)
- エージェント自身の直前の発言と、そこから何発言たったか

state が長いほど遅くなるため、直近の発言数は計測しながら決める。

### 質問(1回の呼び出しにまとめる)

| 名前 | 型 | 内容 |
|---|---|---|
| `should_interject` | noul | 気の利く進行役なら、いまこの瞬間に口を挟むか |
| `intent` | choice | 挟むなら何をするか(下の5択) |
| `addressed_to_ai` | noul | 最新の発言はエージェントに直接話しかけているか |

`intent` の選択肢:

| 選択肢 | 意味 |
|---|---|
| `fact_check` | 参考資料と食い違う数字・事実が出た |
| `answer_question` | 誰も答えられない質問が宙に浮いている |
| `recap` | 決まったことが曖昧なまま次の話題に移ろうとしている |
| `nudge_back` | 議題から大きく脱線している |
| `stay_silent` | 何もしない |

公式例にならい、noul にも `criteria`(true/false それぞれの意味)を書く。選択肢の説明文の書き方で判定が大きく変わるため、ここが調整の中心になる。

### 方針(コードで決める部分)

1. `addressed_to_ai` が高ければ、ほかの条件に関係なく応答する。`intent` が `stay_silent` でも `answer_question` として扱う
2. `should_interject` がしきい値以上で、かつ `intent` が `stay_silent` 以外なら挟む
3. ただし `intent` の confidence が基準値(初期値 0.9、開発用台本で調整)未満のときは黙ってログにだけ残す(迷ったら黙る)
4. 直前に発言してから一定の発言数がたつまでは挟まない(クールダウン)

しきい値は開発用の台本だけで調整し、評価用の台本では動かさない(7章)。

### 変更(2026-10-22、開発用台本での調整結果)

上の「choice 1つ+noul 2つ」では、判定が直近の会話全体に引きずられた。質問があった、脱線した、といった値が問題の発言を過ぎても高いまま残り、`should_interject` も場面による差がほとんど出なかった。そこで次のように変えた。

- 質問を意図ごとの狭い noul 5つに分ける(contradicts / unanswered / drifted / closing / addressed)
- state を「EARLIER LINES」と「LATEST LINE」に分け、質問では最新の発言を指す
- 方針は優先順に、しきい値を最初に超えたものを採る: addressed 0.30 → contradicts 0.35 → unanswered 0.55 → closing 0.50 → drifted 0.62。クールダウンは3発言(addressed のみ無視)

開発用台本での近似計算(AIの発言を履歴に入れない)では、挟む/黙るの一致が81%から91%に、挟むべき7か所での意図の一致が1から5に上がった。判定は質問5つで約1.5秒になった。

## 5. 挟むと決めた後(Bedrock 側)

Strands Agent を1つ用意し、`intent` に応じて指示を切り替えて呼ぶ。

- モデル: Amazon Bedrock 上の Claude Haiku 4.5(公式例と同じ。開発に使ったアカウントで呼び出せることを確認済み)
- ツール: `lookup_reference`(参考資料から該当箇所を引く。`fact_check` と `answer_question` で使う)
- 出力: 1〜2文の短い発言。macOS の `say` で英語の読み上げ

## 6. 再利用できる部品(提出必須)

リポジトリの `kuuki/gate.py` に、会議以外にも流用できる形で切り出す。

- `InterjectionGate`: 会話履歴を受け取り、「挟む/黙る」と意図・確率を返す。LLM を呼ぶ前に置く使い方
- `InterjectionIntervention`: 同じ判定を `InterventionHandler` として包んだもの。Slack への投稿など「発言する」ツールを持つエージェントの `before_tool_call` に差し込み、`Proceed` か `Guide` を返す
- 質問と選択肢の定義、しきい値の意味、使い方を README に短く書く

`InterjectionIntervention` は、黙るべき場面で `Guide` を返すとエージェントが発言ツールを呼び直し、判定が繰り返される恐れがある。そこで `Guide` のフィードバック文は「今回は発言せずにターンを終える」とし、同じターン内の再試行に上限を設ける。本体のデモでは使わない部品なので、最小の動作例を `examples/` に1本置き、動かして確認してから README に載せる。

想定する流用先は、チャットのグループに常駐するボット、配信のコメント欄に反応するエージェント、ペアプロ中に口を挟むコーディング支援など。

## 7. 計測(加点対象)

### 比較する構成

- A: Decider 2B ゲート(提案構成)
- B: 同じ3つの判定を Bedrock の Haiku 4.5 に JSON で答えさせるゲート

### 計る値

- 1発言あたりの判定遅延(中央値・95パーセンタイル)
- 会議1回分の Bedrock のトークン数と料金(料金は記事執筆時に公式の価格表で確認する)
- 正解ラベルとの一致(挟むべき発言を挟めたか、挟むべきでない発言で黙れたか)

遅延は、入力長ごとの初回リクエストと、温まった後のリクエストを分けて記録する。

### 台本と正解ラベル

- 開発用と評価用の2本の台本を用意する(英語、各40発言前後、架空のスプリント計画会議)
- 正解ラベルは台本作成時に付け、本人の確認を受けてから使う
- しきい値や選択肢の説明文は開発用だけで調整する。評価用で調整すると、初めて見る会議でどれだけ当たるか(汎化)の数字にならないため

## 8. 画面(デモ動画用)

ブラウザの1枚のページに、次を並べる。

- 左: 会議の発言が流れるチャット欄。エージェントが挟んだ発言は色を変える
- 右: 発言ごとの `should_interject` の確率バーと、`intent` の上位候補、判定にかかったミリ秒
- 下: 累計の LLM 呼び出し回数と、「毎回 LLM に判定させた場合」との差

実装は FastAPI と Server-Sent Events(サーバーから画面へ一方向に送り続ける仕組み)で作る。

### デモ動画(3分未満が必須)

1. つかみ: 会議にAIを入れると、しゃべりすぎて邪魔になる
2. 黙る場面: 普通の議論が続く間、確率バーは低いままで LLM も呼ばれない
3. 挟む場面: 数字の言い間違いに事実確認、脱線に一言、宙に浮いた質問に回答
4. 計測値: 判定の遅延、LLM 呼び出し回数と料金の差、再利用部品の紹介

## 12. 未確定・リスク

- M1 での遅延が公称値より大きい可能性がある。1章の「実時間で口を挟む」体験が成り立つかは、手順1の計測で判断する。入力長ごとの初回の遅れは、起動直後に台本の典型的な長さで温めておくことで避ける
- `pip install` 版に MLX がまだ入っていないため、MLX で動かすならリポジトリを clone して入れる必要がある
- Python 3.14 では依存ライブラリが揃わない可能性があるため、uv で 3.12 を指定する
- 発言の数が40程度では統計的な結論にはならない。記事では件数を明記し、傾向として書く

## 12.5 手順1の計測結果(2026-10-22、Apple M1・16GB、`--device mlx`)

| 直近の発言数 | 入力トークン | 初回 | 温まった後の中央値(10回) |
|---|---|---|---|
| 4 | 401 | 3,603ms | 988ms |
| 8 | 457 | 1,012ms | 1,004ms |
| 12 | 531 | 1,223ms | 1,213ms |

- 3問まとめて1回あたり約1.0〜1.2秒、質問1つだけなら約0.55秒(8発言、中央値)
- 起動直後の1回目だけ約3.6秒かかった。2回目以降は入力長が変わっても大きくは遅れなかった
- 会議の発言の間隔は数秒あるため、実時間で判定は間に合う見込み。Haiku 4.5 との比較は未計測
- 試しに3場面を流すと、数字の誤り→`fact_check`(0.62)、脱線→`nudge_back`(0.66)、話しかけ→`addressed_to_ai`(0.65)と、方向は合っていた。ただし `intent` の confidence は0.3〜0.6で、初期値0.9では一度も挟まない。基準値は開発用台本で決める
