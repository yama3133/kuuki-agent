しきい値は開発用台本(dev.jsonl)だけで決め、評価用台本(eval.jsonl)では変えていない。発言の生成結果が次の判定の入力に入るため、同じ台本でも実行ごとに数字が揺れる。各1回の実行結果。

## 読み取れること

- 当たり具合は同程度。評価用では挟む/黙るの一致が同じ86%
- Bedrock の呼び出し回数とトークンは、Decider ゲートのほうが大幅に少ない(評価用で入力トークン約81%減)
- 判定の速さは、この M1 では Haiku 4.5 のほうが速い。Decider は5問で約1.6〜1.7秒かかる(内訳は下の「判定速度の改善を試した結果」)。README の 115ms は RTX 3090 での1問あたりの値で、この環境とは条件が違う
- Haiku 4.5 は 0 か 0.95 のような極端な値を返し、Decider は中間の値を返す。この差が判定の質にどう効くかは、この件数では言えない
- 件数が少ない(挟むべき発言が計13)ため、傾向として扱う

生データ: `results/eval_decider.jsonl`、`results/eval_baseline.jsonl`

## 判定速度の改善を試した結果(2026-10-22、サーバー側 latency_ms の中央値)

開発用台本の14発言目までを状態にして計測。

| 条件 | 遅延 | 入力トークン |
|---|---|---|
| 現行(質問5つ、説明文あり、直近8行、MLX) | 1,582ms | 755 |
| 質問1つ | 816ms | 385 |
| 質問3つ | 1,241ms | 581 |
| 質問の説明文(criteria)を外す | 1,343ms | 702 |
| 直近4行に減らす | 1,438ms | 678 |
| ごく短い状態+質問5つ | 1,095ms | 477 |
| 質問文を短くし説明文なし+直近4行 | 1,257ms | 591 |
| MPS(PyTorch)で現行と同じ条件 | 3,294ms | 755 |

- 公式資料では、質問を増やしてもほぼ時間は増えない(状態を1回だけエンコードして共有するため)とあるが、M1 では質問1つにつき約0.2秒ずつ増えた
- MPS は MLX の約2倍遅い
- 入力を削る方向で最大でも約2割の短縮にとどまり、Haiku 4.5 ゲート(945ms)より速くはならなかった。削ると判定の当たり具合が変わるため、しきい値の調整し直しも必要になる
- 結論として現行の設定を維持する。速度は M1 の処理能力が上限と考えられるが、他の Mac や GPU では試していない
